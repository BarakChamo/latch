## Install the CLI

From your downloads directory, run:

```sh
curl -fsSLO https://github.com/BarakChamo/latch/releases/latest/download/install-latch-plugin.sh &&
  sh install-latch-plugin.sh --install-cli
```

The installer selects and verifies the binary for macOS or glibc Linux
on ARM64 or x64. It installs into `~/.local/bin`. If that directory is
missing from your `PATH`, add the following to your shell startup file.

```sh
export PATH="$HOME/.local/bin:$PATH"
latch --version
```

Set `LATCH_INSTALL_DIR` to an absolute directory for a different destination.

### npm tarballs

Install with Node.js 18 or later. Download `barakchamo-latch-0.1.5.tgz`
and the matching binary tarball from the
[GitHub release](https://github.com/BarakChamo/latch/releases/tag/v0.1.5).

| Platform | Binary tarball |
| --- | --- |
| Apple Silicon Mac | `barakchamo-latch-darwin-arm64-0.1.5.tgz` |
| Intel Mac | `barakchamo-latch-darwin-x64-0.1.5.tgz` |
| Linux ARM64 | `barakchamo-latch-linux-arm64-0.1.5.tgz` |
| Linux x64 | `barakchamo-latch-linux-x64-0.1.5.tgz` |

In the directory containing the downloads, install both files together.
For example, on Linux x64:

```sh
npm install --global --offline ./barakchamo-latch-0.1.5.tgz ./barakchamo-latch-linux-x64-0.1.5.tgz
latch --version
```

Start your harness from a terminal that can run `latch --version`.

### Cargo

With Rust 1.88 or later, clone the release tag and install from the checkout.

Run `cargo --version` first. If you installed Rust with rustup and the
shell cannot find Cargo, open a new terminal or run `. "$HOME/.cargo/env"`.

```sh
git clone --branch v0.1.5 https://github.com/BarakChamo/latch.git
cd latch
cargo install --locked --path crates/latch
latch --version
```

See the [build guide](https://github.com/BarakChamo/latch/blob/main/docs/releasing.md#build-the-artifacts)
to build a bundled plugin and CLI together.

Once `latch --version` works, follow the [harness setup guide](/docs/plugins)
to enable automatic checks in your agent.

## Try the CLI in your project

From the directory that contains your check configuration or package
scripts, resolve and run a check. For example, add this to your
`latch.json` if `make lint` is your project command.

```json
{
  "hooks": {
    "turn_end": { "commands": "make lint" }
  }
}
```

```sh
latch status
latch run turn_end
```

A passing check is quiet and exits 0. Make an edit that fails your lint
rule and run `latch run turn_end` again. It reports the lint error and
exits 1. Undo the test edit and run it once more to confirm the pass.
Manual runs execute immediately from the current directory.

## Commands

Run these commands from the directory containing your `latch.json` or
[package scripts](/docs/project-scripts).

| Command | What it does |
| --- | --- |
| `latch config init` | Create a starter `latch.json` in the current directory. Existing files are preserved. |
| `latch --help` | List available commands. |
| `latch --version` | Print the installed version. |
| `latch status` | Show the resolved checks and recent prompt and automatic-check activity without running anything. |
| `latch run after_edit` | Run all configured edit checks immediately. |
| `latch run turn_end` or `latch` | Run all configured turn-end checks immediately. |
| `latch explain after_edit` | Show the resolved edit commands, settings, and filters as JSON. |
| `latch explain turn_end` or `latch explain` | Show the resolved turn-end configuration as JSON. |
| `latch output <log-or-id> [--grep <text>]` | Replay a saved failure or search its original output. |
| `latch output --prune` | Remove expired output across projects in your user cache now. |

Manual runs bypass Git change detection and file filters. Successful output is
quiet by default. Failed commands print their output, and
[`on_failure`](/docs/configuration#hook-fields) controls how many commands run.
`latch explain` never executes commands. Its `config` field is the path to
the `latch.json` file it read, or `null` when no file was present.
`configured` can still be `true` when Latch discovers a package script.

| Exit code | Meaning |
| --- | --- |
| `0` | The operation succeeded. |
| `1` | A check, configuration, or retrieval failed, including a search with zero matches. |
| `2` | The command-line arguments were invalid. |

For commands launched by a harness, see the
[plugin reference](/docs/plugins#integration-commands).

## Retrieve saved output

When a failure report gives a `Saved log` path, open or search that
`.log` file with your editor or your agent's file tools. For byte-for-byte
replay on the original streams, pass the saved log path, filename, or ID
to `latch output` from the same project.

```sh
latch output <id>
latch output <id> --grep 'test_create_user'
```

Full replay sends the original bytes to stdout and stderr. Search matches a
literal, case-sensitive string and returns up to 40 lines per stream, with
long lines shortened around the match.

The cache is under `$XDG_STATE_HOME/latch/output-v1`, or under
`~/.local/state/latch/output-v1` by default. On Windows the fallback uses
`%LOCALAPPDATA%` when available. Saved output may contain sensitive text
printed by the check. Entries expire after seven days. Latch sweeps expired
files across projects during normal use, with an hour between successful
sweeps. Each project keeps up to 64 entries and 64 MiB.
A command with more than 16 MiB of combined output still gets a preview
with an explanation that full output could not be saved.

Run `latch output --prune` to sweep immediately. On machines that rarely
run Latch, schedule that command as the same user with the same state directory.
