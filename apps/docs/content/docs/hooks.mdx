---
title: Hooks and feedback
description: Understand what triggers a check and where each harness shows its result.
---

Plugins map their agents’ native hooks to the same Latch events. Commands
come from the project’s [package scripts](/docs/project-scripts), optional
[`latch.json`](/docs/configuration), or both.

## When checks run

| Event | Trigger | Default comparison |
| --- | --- | --- |
| `after_edit` | A native edit tool finishes. | Immediately before and after that edit. |
| `turn_end` | The agent finishes a turn. | The start and end of the turn, including changes made through shell commands. |

A pre-existing dirty file triggers a check only if it changes again during
the comparison window. Latch checks Git-visible files and runs the commands
without change-based filters when a reliable comparison is unavailable.
Use [path or extension filters](/docs/configuration#examples) to run just
the checks that match the files changed during the event.

Linked worktrees have their own change baselines, whether they sit inside
the main checkout or beside it. Start Latch or your harness from the
directory where you want to read config and run commands. Path filters are
relative to that Git worktree’s root. Edits inside an untracked nested
checkout do not trigger checks in the parent checkout.

These tables cover shipped integrations in local sessions. For hosted
environments, see [Cloud sessions](/docs/cloud).

| Harness | Native edit tools |
| --- | --- |
| Codex | `apply_patch` |
| Claude Code | `Edit`, `Write`, `MultiEdit`, `NotebookEdit` |
| GitHub Copilot CLI | `create`, `edit`, `str_replace_editor`, `apply_patch` |
| OpenCode v1 | `edit`, `write`, `apply_patch` |
| OpenCode v2 | `edit`, `write`, `patch` |
| Pi | `edit`, `write` |
| OpenHands CLI | `file_editor` write operations |
| Kimi Code CLI | Use `turn_end` for automatic checks. |
| Grok Build | `write`, `search_replace`, and patch tools |

## Where reports appear

Passing checks are silent by default. Most integrations attach edit reports
to the tool result in the same turn.
OpenHands sends edit and turn-end reports on the next prompt. Turn-end
reports follow the harness’s lifecycle.

| Harness | Turn-end feedback |
| --- | --- |
| Codex | App-server hook warning. The tested `codex exec --json` output omits it. |
| Claude Code | Informational hook event. |
| GitHub Copilot CLI | Hook warning. |
| OpenCode v1 | TUI toast or headless stderr. Failed reports are added to the next prompt. |
| OpenCode v2 | Server stderr. Failed reports appear in the next prompt's model context. Use `opencode --standalone --print-logs run "..."` to see the report immediately from the CLI. |
| Pi | A message in session history, visible to the next model request. |
| OpenHands CLI | The next user prompt in the same conversation. |
| Kimi Code CLI | The next user prompt in the same conversation. |
| Grok Build | Hook stderr. Model delivery of edit reports remains unverified. |

In Codex, Claude Code, and Copilot CLI, the turn-end warning is for the user
or event stream. The model gets the failure on your next prompt in the same
session and project. Copilot uses
`userPromptTransformed` to attach the report to the prompt. A failed check
lets the turn finish normally.

Use [compact failure output](/docs/configuration#compact-failure-output)
to keep useful lines such as errors and assertions. When a report includes
a saved log path, the agent can read the original output directly or use
[the plugin tool](/docs/plugins#look-up-details-from-a-failure).

## Act on a turn-end failure

Install Latch from a [locally built archive](https://github.com/BarakChamo/latch/blob/main/docs/releasing.md#build-the-artifacts) to try this option
in the current source. Set this top-level option in `latch.json` to let a
compatible agent act on a failed turn-end check immediately.

```json
{
  "turn_end_feedback": "continue_once"
}
```

Keep your existing check definitions or package scripts. A supported harness
gets one follow-up containing the failure without a new message from you. Latch does not rerun the turn-end checks for that follow-up.
Successful checks, manual runs, and the default `report` mode keep their
usual behavior.

Codex, Claude Code, Copilot CLI, OpenCode v2, Pi, OpenHands CLI, and Kimi Code
CLI have a continuation path. OpenHands and Kimi are verified at the hook
protocol level. Native stop hooks that use an active-stop flag need a
harness version that supplies it. OpenCode v1 and Grok Build keep their
default delivery. Use `after_edit` for fast checks and ask the agent to
call `run_turn_end` before responding when you need feedback in a session
without continuation.
